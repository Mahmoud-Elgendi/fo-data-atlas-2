# Private analyst pilot: 20 acceptance scenarios

Status: planned manual scenarios, not a completed certification suite. Use a clean PC, an authorized second user, the published package and recipient-owned fixtures. Record host/version/profile, requested grain, evidence/source identities, target schema fingerprint, actual outputs, unresolved gaps and pass/fail per scenario. Keep credentials and live result files outside the plugin repository.

| # | Scenario | Required observable outcome |
|---:|---|---|
| 1 | Clean-PC private installation | Authorized user obtains the published tools and chosen metadata without developer-machine paths. |
| 2 | Project-only setup | Only intended project registration/configuration is prepared; activation instructions are clear. |
| 3 | Compatible tools update | Verified metadata cache reused; project schema/source choices preserved. |
| 4 | Cancel setup/update | Previously usable installation remains intact; unaccepted metadata download does not start. |
| 5 | Codex native activation | Skill is actually discoverable and completes one evidence request in a new chat. |
| 6 | Claude native activation | Namespaced skill is actually discoverable and completes one evidence request. |
| 7 | Metadata use without network | Installed originals remain readable when release checking is unavailable. Host inference connectivity is stated separately. |
| 8 | Core missing original | Agent identifies the missing payload and offers Full; it does not silently search raw exports or invent content. |
| 9 | View SQL/dependencies | Original definition and underlying views/tables are retrieved with same-source identities; missing prerequisites are explicit. |
| 10 | Purchase order query | Confirmed line grain; retained-line cardinality and actual target columns checked. |
| 11 | Receipt monetary query | Posted versus current-rate amounts distinguished; version/line grain and source evidence are explicit. |
| 12 | Vendor invoice request | Starter/example coverage limits disclosed; missing joins/fields not disguised as validated output. |
| 13 | Status text | Target entity/option set/language used; codes preserved; duplicate labels and unmatched codes checked. |
| 14 | Ambiguous workflow timing | One short question resolves event versus instance grain before SQL is drafted. |
| 15 | Consecutive event intervals | Next retained event determines end; last end/duration NULL; preview limits do not truncate windows. |
| 16 | Multiple submissions | Chosen first/latest definition honored across instances; matching submitter retained; no unintended timesheet duplication. |
| 17 | Company casing | Target evidence guides consistent ranking/join normalization; result counts and independently selected values agree. |
| 18 | Different target table ID | Index prefix/SQL object_id rejected as proof; recipient F&O table ID confirmed before a context filter is supplied. |
| 19 | Resource polymorphism | RefTableId/RefRecId, partition and company constraints retained; wrong object types do not match. |
| 20 | Output-name compatibility | Named aliases preserved; raw wildcard/legacy-view differences stated; no unrequested employee enrichment or fabricated keys. |

Fixture tests cover selected workflow/resource invariants, not these complete host/installation/business journeys. A successful SELECT alone does not establish financial or F&O UI reconciliation. For each pilot failure, preserve a minimal sanitized reproducer and fix the actual failing boundary before broadening scope.
